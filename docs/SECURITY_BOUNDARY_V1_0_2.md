# v1.0.2 공개 API와 공격 표면 구분

## 공개 가능 / 제한 대상

| 분류 | 예시 | 정책 |
|---|---|---|
| 공개 라이브러리 API | `Banner`, `Distribution`, `RateMode`, `GameSetup`, 환급 추정 계약 | SemVer 1.x 호환성 보존, CI 회귀 테스트 |
| 바이너리 내부 구현 | `src/app/*`, `src/data/*`, `src/ui/*` | `pub(crate)` 이하, 임의 외부 import 금지 |
| 데이터 자산·이미지·확률 모델 | TSV, PNG, 공개 계산 규칙 | 저장소가 Public인 이상 내용 공개. 비밀 보안 모델로 사용하지 않음 |
| 비밀키·토큰·서명 인증서 | PAT, API 키, 개인키, Windows Code Signing 인증서 | 절대 소스/릴리즈에 포함 금지. GitHub Secrets/전용 비공개 보관소에서만 운용 |

**한계:** `pub(crate)`는 Rust 타입 접근 제어입니다. 공개 저장소의 소스나 사용자의 기기에 전달한 바이너리 자체를 숨기거나 난독화하지 않습니다. 악성 코드가 동일 사용자 권한을 얻었거나 GitHub 저장소 관리자 권한이 탈취된 상황에서는 별도의 신뢰 루트와 운영상 보호가 필요합니다.

## 이번 버전의 실제 방어 변경

1. 업데이트 다운로드는 GitHub 소유 경로·커밋 SHA·정확한 데이터 파일/이미지 패턴만 허용합니다. `curl --disable`로 개인 설정 옵션 로딩을 막고 기존 HTTPS/리다이렉트/크기/시간 제한을 유지합니다.
2. 언어 환경 파일은 비공개 임시 파일에 기록한 후 교체하며 기존 링크를 거부합니다. 원본을 손상시키지 않는 실패 경로를 테스트합니다.
3. 공격자가 제공할 수 있는 CSV 헤더는 64개 이하로 제한하고 중복 검사를 해시 기반으로 변경합니다.
4. 카탈로그 매핑 검증은 사전 계산된 캐릭터 키 집합을 사용합니다. 입력은 여전히 최대 3000개 항목, SHA-256 이미지 및 정합성 검사 조건을 지켜야 합니다.
5. CI는 바이너리 전용 코드의 불필요한 public 노출과 Git에서 추적된 고위험 비밀 파일명 패턴을 검사합니다. 기존 Cargo.lock·SHA-256·RustSec·ClamAV·실제 GUI 스모크를 계속 실행합니다.

## 미해결 위험 및 운영 조치

- **저장소가 Public:** 이미 공개된 코드·이미지·알고리즘은 접근 제어로 비공개화할 수 없습니다. 반드시 비밀로 유지할 자산은 저장소 밖에 두어야 합니다.
- **GitHub 쓰기 권한 침해:** 커밋 SHA 고정은 전송 도중 파일 섞임을 막지만, 침해된 관리자가 승인한 악성 커밋을 거부하지는 못합니다. 브랜치 보호, 필수 PR 검토, 2FA/패스키, 최소 권한과 릴리즈 승인 정책을 저장소 운영에서 적용해야 합니다.
- **바이너리 신원:** SHA-256은 동일 파일 무결성 검사이지만 게시자 신원을 인증하지 않습니다. Windows Authenticode 서명과 키 보호는 별도 인증서가 필요하며 현재 제공되지 않습니다.
- **실행 환경 침해:** 같은 사용자 권한을 가진 악성 프로세스나 관리자 권한 악성코드는 프로그램 데이터 또는 실행 파일을 바꿀 수 있습니다. OS 권한·백신·다운로드 출처 확인과 격리를 병행해야 합니다.
- **업데이트 신뢰:** 현 자동 데이터 업데이트는 GitHub의 승인된 `main`이 신뢰할 수 있다는 가정 아래 동작합니다. 저장소 침해에 대한 강한 방어는 오프라인 공개키 서명/별도 서명 권한 및 검증된 릴리즈 매니페스트 도입이 추가로 필요합니다.
- **파일 시스템:** Windows의 설정 파일 교체는 임시 파일을 충분히 기록한 뒤 기존 파일을 제거하므로 완전한 POSIX 원자적 교체와 다릅니다.
- **성능:** 책임 분리 자체는 실행시간 개선을 보장하지 않습니다. 이번 확실한 복잡도 개선은 CSV 열 중복 검색 및 카탈로그 연결 검증입니다. FFT 등 기존 성능 경로도 별도 벤치마크로 측정해야 합니다.
