# v1.0.0 출시 준비 — 요구사항 전수 분해 및 검증 행렬

> **역사적 검토 문서:** 최초 v1.0.0 출시 준비 당시의 상태·브랜치·검증 계획입니다. 이 표의 과거 상태를 현재 v1.0.3에 그대로 적용하지 마십시오. 현행 배포·보안과 실측 성능은 [보안 배포 안내](SECURE_RELEASE_v1_0_3.md) 및 [성능 보고](PERFORMANCE_V1_0_3.md)에 있습니다.

**기준:** v0.2.7 정식 릴리즈(`62a97dec945cb950d9ac4ed0292c5c0e7b34bea1`). 작업 브랜치: `refactor/v1-stable-modules-and-validation`.

## 범위와 판정

코드/DB가 아닌 Rust 데스크톱 프로그램이므로 네 게임의 계산 로직, 사용자 입력, 게임 데이터, 로컬 파일과 업데이트, 배포 인프라를 범위로 합니다. **외부 게임의 비공개 내부 로직이나 모든 자산의 원작자 라이선스는 저장소의 코드만으로 입증할 수 없습니다.** 이를 ‘검증 완료’로 표시하지 않습니다.

v1.0.0은 **지원 범위 내 공개 인터페이스와 설치 결과의 안정성**을 의미하며 게임에서 절대적으로 정확한 뽑기 결과를 보증하지 않습니다. 상태 표기는 ‘반영’(코드 적용), ‘신규 테스트’(검증 추가), ‘CI 검증’(성공해야 완료), ‘기존 검증’(v0.2.7의 증거 존재), ‘부분/미검증/정보 부족’(출시 후에도 제한 명시)을 구분합니다.

## 실행 흐름 및 승인 게이트

1. **조사·설계:** 기존 `src/*.rs`와 `scripts/`/Actions/TSV/이미지 매니페스트의 계약을 식별하고 공개 API를 고정합니다.
2. **최소 단위 실행:** 각 경계 조건을 재현 가능한 테스트로 만들고 독립된 파일 단위로 변경합니다.
3. **책임 분리:** `probability/`, `domain/`, `analysis/`, `data/`, `ui/`, `app/`로 나누되 `#[path]`와 crate-root `include!`로 기존 private 호출 계약을 보존합니다.
4. **알고리즘:** 정확한 DP 의미와 확률 질량을 유지하며 0 확률 상태 연산을 생략합니다. 입출력/수행 경로 변경이 있으면 근거 있는 테스트가 우선입니다.
5. **1차 CI:** Windows/Ubuntu `cargo test --locked --all-targets`, `cargo clippy --locked --all-targets -- -D warnings`, `cargo doc`, 이미지·보안 검사.
6. **2차 실제 GUI:** Linux Xvfb GUI 시작, 9장 이상 화면 스냅샷, Windows release exe와 Image 679개 포함 여부 검증.
7. **최종 비교:** 이전 릴리즈 대비 목표·재화·게임별 선택·확률 모델/추정 경계를 다시 검토합니다.
8. **승인:** 실패 시 `main`은 유지하고 PR 브랜치에서 원인 수정 후 재실행합니다. 모든 필수 검증이 성공한 동일 커밋만 병합합니다.
9. **정식 배포:** `main` CI 성공, `v1.0.0` 태그 일치, ZIP/exe/SHA256SUMS 총 5개 자산을 검증해 종료합니다.

## 차단 조건 / 남은 리스크

CI 실패, 공개 API 파손, 확률질량 보존 실패, 배너 전용권 중복 계산, 이미지/Manifest 검증 실패, 태그 충돌이 하나라도 발생하면 **릴리즈 중단**입니다.

별도 사람의 최종 판단/확인이 필요한 사항은 제3자 이미지 배포 라이선스, 미공개 확률 가정과 최신 수집 데이터, Windows 인증서 코드 서명, 실제 기기 GUI 접근성 검증입니다. 이 항목들은 1.0.0에서 명시된 지원 범위 밖이거나 기존 제품에서 유지 중인 제한입니다. 완료라고 주장하지 않습니다.
