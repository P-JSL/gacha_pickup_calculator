# 성능 및 검증 기준

**계측 가이드 기준: v1.0.18**

## 알고리즘

- 밀집 확률질량분포(PMF): 조건에 따라 FFT 합성, `O(N log N)`. 작은·희소 분포는 직접 합성하며, 항상 FFT를 택하지는 않습니다.
- 정렬된 누적분포(CDF) 분위수: `O(log N)` 이진 탐색.
- 환급 Monte Carlo: 입력된 표본 수 N에 비례한 샘플링. 고정 시드로 작업자 수에 관계없이 재현성을 유지하고, CPU/표본 수에 따라 최대 8개 작업자를 사용합니다.
- 결과 UI는 계산 워커 종료 신호를 사용하고, 버튼 클릭 전 입력 변경으로 Monte Carlo를 자동 실행하지 않습니다.

## 재현 방법

```sh
cargo test --locked --all-targets
cargo test --locked --release --test performance_regression -- --ignored --nocapture
```

`tests/performance_regression.rs`에서 직접 합성/FFT 및 분위수 결과의 정확성을 비교하고 같은 환경에서 실행 시간을 기록합니다.

## G-06~G-09 실제 최적화 구현 (2026-11-12)

**G-06 — 정렬:** 대량(16,384개 이상) 환급 시나리오는 `(initial_flexible_required, raw_pulls)` 키의 의미상 유효 바이트만 이용하는 **제자리 MSD American-flag radix sort**를 사용합니다. 소규모 배열·짧은 부분 구간은 기존 비교 정렬로 처리합니다. 결과 배열 자체를 복제하지 않으므로 보조 결과 저장량은 표본 N에 비례하지 않습니다. 모든 시나리오의 필드, 원본 추첨 순서의 `raw_pulls`, 정렬된 예산 `budgets`, 조건부 성공률·환급 수치는 유지합니다. 단, 두 키가 *완전히 동일한* 경로들의 내부 순서는 기존에도 지정되지 않은 순서이며, 비교에선 키/전체 자료 보존을 검증합니다.

**G-07 — 동적 작업자 풀:** 명조의 산호 교환 0·1·2 전략은 더 이상 3개의 고정 자식 워커 묶음을 별도로 만들지 않습니다. 전체 CPU 상한(최대 8개) 내에서 하나의 공용 큐를 사용하고, 전략별 4,096개 표본 청크를 번갈아 배치합니다. 유휴 워커는 다른 전략의 작업을 즉시 가져올 수 있습니다. RNG는 워커가 아닌 **전략 내 원래 추첨 인덱스**로 시드가 결정되므로 할당 순서와 결과의 bitwise 재현성은 분리됩니다. 기존 전략 3개를 모두 계산하며 결과 목록 및 선택된 전략 참조 형태는 유지합니다.

**G-08 — 이미지 렌더링:** 디코딩·해시 검증·Lanczos3 리샘플링과 비동기 작업 세대는 그대로 두고, 이미 제출한 캐릭터/전용 장비 텍스처 캐시에 **192개 제한과 LRU 제거**를 적용합니다. 캐시에서 밀려난 이미지는 다시 화면에 나타날 때 백그라운드에서 재로딩합니다. 현재 보이는 이미지는 매 프레임 마지막 사용 시각이 갱신됩니다. 이는 GPU 텍스처의 *상한 설정*이며 모든 상황에서 프레임률이 개선됐다는 주장은 아닙니다.

**G-09 — 로그 배치:** `log/session.log` 경로와 매 실행 초기화, 내부 검색·복사 창은 유지합니다. 평상시 INFO 로그는 16 KiB BufWriter를 통해 최대 **32건 또는 약 250ms** 단위로 파일 버퍼를 flush합니다. GUI가 최소화되어도 별도 가벼운 타이머가 약 100ms 간격으로 flush 만료를 검사합니다. **WARN/ERROR, 프로그램 시작/종료, 최종 계산 결과와 로그 통계는 즉시 flush**하고 정상 종료 시 잔여 버퍼까지 처리합니다. 하드 종료·정전에서는 아직 디스크에 쓰지 않은 INFO 로그가 유실될 수 있으며, `flush`는 `fsync`가 아닙니다. 손실이 전혀 허용되지 않는 운영 환경에서는 배치 설정을 비활성화하거나 sync 정책을 별도로 설계해야 합니다.

본 절은 구현 방식과 데이터 계약을 설명합니다. 최종 성능 개선율은 **동일 하드웨어·동일 실행 조건·동일 표본**에서 이전 커밋과 새 커밋을 비교 측정한 뒤에만 확정할 수 있습니다. 기본 CI/Clippy/회귀 테스트 및 Windows/Linux 실제 실행 검증을 통과하지 않으면 릴리즈하지 않습니다.

## G-05~G-09 초기 계측 기록 (최적화 이전)

이 절은 제자리 정렬·공용 동적 작업자 풀·텍스처 LRU·로그 배치 도입 전의 **기준선 측정 방식**을 보존합니다. 실제 최적화와 기록의 차이는 위의 'G-06~G-09 실제 최적화 구현' 절을 우선합니다. 아래 환경변수는 진단/비교용으로 일반 실행에서 꺼져 있습니다.

### G-05: 전체 표본·CPU 작업자 기준선

다음 명령은 4개 게임의 **100,000/1,000,000 표본 × 1/2/4/8 작업자**, 조건당 3회 반복, 실행시간 중앙값·p95·시나리오 SHA-256 동일성 및 Linux 프로세스 VmHWM 정보를 출력합니다.

```bash
GACHA_PERF_MATRIX=1 GACHA_PROFILE_MONTE_CARLO=1 cargo test --locked --release --test performance_regression -- --ignored --nocapture
```

- 코드 내 계측: `GACHA_PROFILE_MONTE_CARLO=1`을 지정하면 `GACHA_MC_PROFILE`로 결과 배열 초기화(alloc), 추첨(sample), 정렬(sort), 기타 후처리(remainder), 전체(total) 시간을 나누어 출력합니다.
- `GACHA_PERF_MATRIX=1`을 **설정하지 않으면** 고비용 전체 행렬 벤치마크는 실행되지 않습니다. 기본 CI에는 기존 100,000건 성능 회귀 벤치마크가 유지됩니다.
- `VmHWM`은 해당 프로세스의 최대 RSS이며 개별 함수의 peak heap은 아닙니다. Windows에서는 별도 외부 프로파일러 없이는 값을 제공하지 않습니다.
- p95 표본은 조건당 3회로 제한됩니다. 이는 **초기 탐색용**이고 정밀한 분포 추정은 충분한 반복과 동일 CPU·전원 정책·빌드·입력으로 다시 실행해야 합니다.
- 벤치마크의 `requested_workers`는 요청한 상한입니다. 실제 작업자 수는 `available_parallelism()` 및 최소 작업자당 표본 수 정책에 따라 더 작을 수 있으며, 내부 `GACHA_MC_PROFILE`의 `workers`가 실제 수를 나타냅니다.
- 코어 사용률, 입력 시드, 타이밍, RSS, 커밋 SHA를 기록한 뒤 기준선과 수정본을 **동일 환경**에서 측정해야 개선 배수에 의미가 있습니다.

### G-06~G-09의 이전 대안 검토

기존 비교 정렬·고정 작업자 분배·무제한 이미지 캐시·건별 flush에 대한 검토는 이 PR 이전 기록입니다. 이 네 영역은 상단의 실제 구현으로 대체되었으며, **신규 방식의 CI 검증 결과가 기존 버전 대비 속도 향상을 보장하지는 않습니다**. CPU/GPU/파일시스템 특성별 비교 측정은 계속 유효합니다.

### 과거 측정의 해석

2026-11-07의 기존 CI 실험에서는 2,048×2,048 밀집 PMF의 FFT가 직접 합성 대비 약 **3.08배**, 20,000회 분위수 이진 검색이 선형 검색 대비 약 **52.55배**였습니다. 이 값은 **당시 단일 Runner의 특정 마이크로벤치마크** 결과이며, 현행 버전의 모든 환경에서 동일한 속도가 나온다는 뜻이 아닙니다. [실행 기록](https://github.com/P-JSL/gacha_pickup_calculator/actions/runs/42300383443).
